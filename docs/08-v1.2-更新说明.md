# v1.2 更新说明（工具 v1.2 / 发布 v3.3）

日期：2026-10-31
基线：v1.1（v3.2）→ 本版 v1.2（v3.3）

## 1. 只改了"保持/恢复"层，解锁主逻辑未动

未改动：

- live 声明写组（`0x8872C / 0x2241C / 0x8841C / 0x8C2C0 / 0x8C300 / 0x8C040.SPEED / 0x8C1C0 / 0x88610`）；
- 宽度安全配方（`0x8C040 = (cur & ~0xF8000000) | 0x80000000`，回退整字 `0x20085800`，禁止单 bit 清 bit31）；
- 整卡复位预算（live 连续失败才兜底，单次运行最多 1 次、每开机周期最多 2 次、间隔 ≥10 分钟）；
- `-help` / 未知参数守卫（只打印用法，退出码 2，不触发解锁）；
- 驱动部署、策略键写入、编码修复。

## 2. 看门狗 150 ms → 20 ms

常量：`T_HOLD_PERIOD_MS 150 → 20`。

保持循环内部限流同步调整（否则 20 ms 只是"看得更勤"，恢复仍慢）：

| 位置 | v1.1 | v1.2 |
|---|---|---|
| 声明补写限流 | 2000 ms | 200 ms |
| SPEED 补写限流 | 2000 ms | 200 ms |
| 掉速后 retrain 间隔 | 2000 ms（`T_TRIGGER_MIN_GAP_MS`） | **20 ms**（仅保持循环内） |
| 宽度重写稳定等待 | 3000 ms | 500 ms |
| 宽度补写限流 `T_WIDTH_RETRY_MS` | 3000 ms | 500 ms |
| `lowSpeedStreak` 阈值 | 40（≈6 s） | 300（20 ms×300≈6 s，等价） |

实测：掉速 → Gen2 恢复 **0.23 / 0.23 / 0.25 s**；x16 声明恢复 **0.73 / 0.82 / 0.84 s**；
旧版 150 ms 同环境为 4 s / 12–16 s（约快 16–17 倍）。

## 3. 宽度重训（为物理 x16 准备）

`WidthArm()` 成功把 `LnkCap maxwidth` 改成 16 之后，调用 `WidthRetrainOnce()`：

1. 仅当链路已在 Gen2 时执行；
2. `WriteTlsBoth` + `RetrainBoth`（与正常 retrain 相同的安全路径）；
3. 100 ms 后轮询 `LNKSTA` 的 width 位，最多 2 秒：
   - `width==16` → `★ 物理链路宽度已训到 x16`（成功，失败计数清零）；
   - 未到 16 → 失败计数 +1；
   - 期间速度掉回 Gen1 → 立即退出，交保持循环恢复；
4. **每次 `WidthArm` 成功后都会尝试**（目标用户是补了电容的物理 x16 机器，需要每次恢复都重新协商宽度）；
5. 连续 **2 次**未达 x16 → 判定本机未补电容，本进程内停止重训（重启进程可重试）；成功一次则计数清零；
6. 两次尝试间隔 ≥3 秒；单次尝试最长阻塞 ≤2.1 秒；全程 try/catch，异常不影响主流程。

4-lane（无电容）实测：启动阶段重训 1 次（失败 1/2），第 1 次 `-bw` 后重训第 2 次（失败 2/2）→ 日志出现
"连续重训未达 x16，判定本机未补电容，本进程内停止重训"，之后 7 次重新 arm 均 0 次重训；**未掉卡**。

> 物理 x16 是否成功取决于电容改造质量，软件不能保证；工具只负责"声明 + 重训 + 如实报告结果"。

## 4. `-bw`（带宽测试）顺序修复

旧版：测试完 → 等保持进程恢复 → 打印"链路已恢复" → 进程退出销毁 CUDA 上下文 → **又触发一次掉速**，
导致"刚说恢复，马上又掉"。

v1.2：测试 → 打印数字/RESULT → `cuCtxDestroy_v2` → 等恢复（≤30 秒）→ 打印"链路已恢复" → 退出。
实测退出后 0.1–0.2 秒内 `-check` 仍为 Gen2 x4 + 声明 x16。

## 5. 状态面板（`-check` / `状态.cmd`）

- 主证据改为**状态文件新鲜度**（≤5 秒；v1.1 为 15 秒）；`holderSeen`（进程枚举）仅作辅助；
  `inHold = holderSeen || fresh`；
- 四类结论：
  - `!inHold` → `未在保持：保持进程没有运行（链路会回到 Gen1，这是正常的）`；
  - `fresh && !holderSeen` → 仍按已解锁/未解锁判定（文件新鲜必是保持进程写的）；
  - `!fresh && holderSeen` → `状态未知：保持进程在运行，但状态数据超过 5 秒未刷新…`；
  - 其余按速度：`已解锁：Gen2 x4（5.0 GT/s）` / `未解锁：当前 Gen1 x4（目标 Gen2 x4）`；
- `[声明宽度 x16]` 只在数据新鲜时附加（消除"未在保持 + 声明 x16"的矛盾组合）；
- 新增「判定依据」行：数据时间（新鲜/过期）、保持进程（PID / 未检出（权限受限）/ 未运行）、计划任务状态；
- 底部重复的 `RESULT:` 已移除；失效的 `install.cmd` 引用改为 `自动解锁.cmd`。

非管理员实测（`runas /trustlevel:0x20000`，Admin 组 deny-only）：保持进程运行时正确显示已解锁；
枚举不到进程时走"权限受限，按数据新鲜度判定"分支，不再误报"未在保持"。

## 6. 已知限制 / 风险

- 4-lane 机器上，重训失败 2 次后本进程停止重训；环境掉速可能较快用尽预算，需重启保持进程重置；
- 状态文件写失败（磁盘满/权限）会退化为"未在保持"（该场景未实测）；
- 20 ms 看门狗在掉速期间最多 50 次/秒 retrain（写压力约 v1.1 的 7.5 倍），本机未掉卡，长期继续观察；
- 冷启动自启在 v1.1 已实测通过（开机 +102 秒触发、约 5 秒解锁、0 复位）；v1.2 沿用同一任务与路径，未重新做整机冷启动；
- x16 物理成功分支在 4-lane 机器上无法实测，只做了代码路径审查。
