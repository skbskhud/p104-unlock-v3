# P104-100 功能边界总表（2026-10-29 更新）

> 对象：NVIDIA P104-100（GP104，`10DE:1B87`，8 GB GDDR5X）
> 本文只回答一件事：**每一层能力，能不能从主机侧打开；卡在哪一层；证据是什么。**
> 所有数字都是本机实测（Windows 11 / i9-14900KS / HM570 改板 / 驱动 572.75），
> 每条结论标注证据等级，覆盖边界写在最后。

---

## 0. 一句话结论

| 能力 | 结论 | 落点 | 证据等级 |
|---|---|---|---|
| **PCIe Gen2 x4（5.0 GT/s）** | ✅ **可解**，工具已做出（0.78 → 1.55 GB/s） | 寄存器层 | 【实测】可复现 |
| **PCIe 声明宽度 x4 → x16** | ✅ **主机侧可改**（`LnkCap` 最大宽度实时变 x16）；**实际链路宽度未验证**（需物理层） | 寄存器层（声明）+ 物理层（待验证） | 【实测·声明层】/【未验证·链路层】 |
| **PCIe Gen3（8.0 GT/s）** | ❌ **不可解**，OTP 熔丝 `GEN3_DIS=1`，主机/驱动/VBIOS/EFI 全无入口 | 熔丝层 | 【实测】证据链 6 条 |
| **NVENC / NVDEC / OFA 编解码** | ❌ **不可解**，OTP 熔丝 `NVDEC_DISABLE=1`、`NVENC_DISABLE=3`、`OFA_DISABLE=1` | 熔丝层 | 【实测】NVIDIA fuse 命名表 + 否证 |
| （延伸）显示输出 / 硬件光追 | ❌（属 CMP 40HX 的结论，不在本卡） | 熔丝/硬件层 | 见 `矿卡破解边界报告` |

**一句话：寄存器层能解的已经全解了；固件层没有可写入口；熔丝层（Gen3、编解码器）是真正的墙。**

## 2. 限制落在哪一层（四层模型）

| 层 | 能否改 | 本卡对应项 |
|---|---|---|
| ① 寄存器层 | ✅ 能（无需失性写 + 复位/重训） | **Gen2**、**声明宽度 x4→x16** |
| ② 驱动层 | ⚠️ 部分（改 INF/注册表只是表象） | P104 的 `RMPcieLinkSpeed` 等（非必需） |
| ③ 固件层（VBIOS/EFI） | ⚠️ 能改但有风险 | 本项目未依赖；Turing 起 VBIOS 有签名校验 |
| ④ **熔丝层（OTP）** | ❌ **不能**（一次性可编程，主机无写路径） | **Gen3**、**NVENC/NVDEC/OFA** |

判断锁在哪一层的方法与本文证据都来自实测，方法见旧文 `docs/01-技术报告.md`。

## 3. Gen2 x4：可解（寄存器层）

**机制（实测有效，纯 BAR0 写 + 一次链路重训，无需整卡复位）**

```
0x8872C  = (old & ~0xF) | 6     # NV_XVE_FUSE_OVERRIDE
0x2241C |= 0x81                 # NV_PTOP_FS4：GEN2_PCIE / GEN2_PCIE_SPEED
0x8841C &= ~0x6000              # 清 GEN2_DIS（bits 13/14）→ LnkCap2 由 0x02 变 0x06
0x8C040  SPEED[19:18] = 1       # 5.0 GT/s 请求
0x8C1C0  [19:16] = 2            # LNK_CAP_SPEED = 5.0 GT/s
0x88610 |= 1                    # VSEC hierarchy
根端口 LNKCTL2 TLS=3 + Retrain  # 链路实际训练到 Gen2
```

**实测数据**：x4 @ Gen1 H2D 0.780 GB/s / D2H 0.851 GB/s → x4 @ Gen2 H2D **1.549 GB/s** / D2H **1.669 GB/s**
（`LNKSTA=0x00001042`，速度码 2 = 5.0 GT/s）

工具：**`P104-2.0x16-v1.1/`**（v3.2 起随仓库发布）。

## 4. 声明宽度 x4→x16：主机侧可改，物理链路未验证

**新发现（2026-10-28，两次独立复现）**：只写 `0x8C040` bit31 = 1，端点 `LnkCap` 的最大宽度当场从 x4 变成 x16：

| 步骤 | LnkCap |
|---|---|
| 基线 | `0x00453C41`（max speed Gen1，**max width x4**） |
| 写 `0x8872C` 低4位=6 | 不变 |
| 写 `0x8C040` bit31=1 | `0x00453D01`（**max width x16**） |
| 整字写回基线 `0x8C040=0x20085800` | `0x00453C41`（回 x4，链路不掉） |

- 说明：这是 **`LnkCap` 声明层**的可写入口（NVPermissive 的 Pascal 路径里也有对应位：`0x8C040` bit31 是 arm/commit 门，
  `bits[22:18]` 是宽度模式，`bits[1:0]` 是触发位）。**宽度没有熔丝**，所以这一层能动。
- **必须说清楚**：`LNKSTA` 里的实际链路宽度仍然是 **x4**，带宽**没有变化**。
  链路宽度 = min(两端声明, GPU 侧 lane strap, PCB 走线/AC 耦合电容)。
  声明层已经打开，剩下的是物理层——这也是「补 AC 耦合电容」从"肯定没用"变成"唯一有希望的路径"的原因。
- **【未验证】**：补完电容后能否真的训练到 x16、GPU 侧 strap 是否给 16 条 lane、哪些批次板子走线完整。
  社区同型（150HX 补电容有效）是旁证，不能直接外推到 P104。
- ⚠️ 操作注意：**不要单 bit 清 bit31**（会留下半套状态导致链路掉线）；
  回退一律**整字写回基线** `0x8C040 = 0x20085800`。掉卡时完全断电冷启动即可恢复。

工具：`P104-2.0x16-v1.1/一键解锁.cmd`（v3.2 起；Gen2 + 宽度声明一起施加，150ms 看门狗保持，计划任务开机自启）。
**发布定位：这是"声明层实验"，不是"带宽解锁"。**

## 5. Gen3（8.0 GT/s）：不可解（熔丝层）

**结论：不是"没找到方法"，而是设备自己拒绝 + OTP 熔丝锁死。**

证据链（每条都独立）：

1. 端点把 Gen3 目标速率**实时钳回 Gen2**：写 `LNKCTL2.TLS=3`，0.35 s 内回读=2；连写 1000 次全失败（配置空间 + BAR0 镜像两条路径）。
2. `LnkCap2` 的 8GT/s 能力位（bit3）**从未出现**：向量始终 0x02/0x06，从未 0x0E。
3. `LNKSTA2` 的均衡位（Equalization Phase1-3 / Complete）**全程 0** —— 8GT 均衡过程根本没运行。
4. 强制 PHY 速率（XP3G rate=0x00340036，写入成功且回读正确）+ 重训 → 链路仍停在 Gen1/Gen2。
5. **最后一枪（2026-10-28）**：在宽度序列的 arm 状态（`0x8C040` bit31=1）下写
   `0x8C1C0[21:20]=0`（SYSTEM_MAX_SPEED=8GT）→ **硬件拒绝（回读不变）**；
   再 + 8GT 请求 + 根端口 TLS=3 + Retrain + SBR → 仍然没有 8GT 能力位、没有均衡。
6. 熔丝侧：`FUSE_PCIE_GEN3_DIS = 1`（OTP，主机只读，写免疫；同 170HX "任何特权级都没有写端口"）。
   社区 CMP 170HX（有 SEC2/HS 权限）同样从未成功，结论 "Gen2 is a software lockout, Gen3 is a hardware fuse"。

⇒ 主机侧（寄存器/驱动/VBIOS/EFI）**没有任何入口**。理论只剩物理熔丝攻击（开盖/激光/电压毛刺），
成本高、风险大、无公开成功案例，且即使成功 PCIe 仍受硬件掩码约束 —— **不建议，也不在本项目范围**。

## 6. NVENC / NVDEC / OFA：不可解（熔丝层，2026-10-29 定案）

**新证据：用 NVIDIA 自己固件（NVPermissive 1.47MB core）内置的 fuse 命名表，映射到 P104 读取：**

| NVIDIA fuse 名字（固件表原文） | P104 实测值 |
|---|---|
| `NV_FUSE_OPT_NVDEC_DISABLE` | **1** |
| `NV_FUSE_OPT_NVENC_DISABLE` | **3**（两个编码器都禁） |
| `NV_FUSE_OPT_OFA_DISABLE` | **1** |
| `NV_FUSE_STATUS_OPT_NVDEC` / `_NVENC` / `_OFA` | 1 / 3 / 4（同向） |
| `NV_FUSE_FLOORSWEEP_PRIV_LEVEL_MASK` | `0xBADF5040`（PLM 保护区，符合预期） |

配套否证（都做过）：

- 媒体窗口 5 个（PVDEC `0x84000` / PPDEC `0x85000` / PVENC `0x1C8000` / `0x1C2000` / PMEDIA `0x200000`）
  各 64 dword：**100% 哨兵**（0xBADF1100/1201/1301/5040），0 个真实值。
- `PMC_ENABLE` 的媒体位本来就是 1（不是 PMC 门控）。
- 零售 GTX 1070 的 VBIOS DevInit 会置 `PMC_ENABLE` bit30（PRIVRING），P104 的 DevInit 显式清 0（VBIOS 差分实测）；
  运行期置 1 后媒体窗口仍全哨兵。
- 媒体引擎 PMC 位 clear→set 复位脉冲（MSPPP/MSVLD/MSPDEC/bit18）全部试过 → 仍全哨兵。

⇒ 三块引擎在**地址解码层就被熔丝关闭**，主机侧无解。
这也解释了历史现象：媒体窗口全哨兵、`nvEncodeAPI` 能建会话但初始化崩溃（0xC0000005）、任何驱动/VBIOS/EFI 补丁无效。
要编解码只能换卡（GTX 1060/1070/1080 等零售卡）。

## 8. 覆盖边界与安全（诚实声明）

- 所有硬件结论只针对：**P104-100（GP104，10DE:1B87）**、本机平台（Win11 / HM570 改板 / 驱动 572.75）。
  换平台/换卡/换驱动后结论可能不同。
- 寄存器访问通过两个公开签名的内核驱动（WinRing0x64.sys + ThrottleStop.sys）完成；
  安全软件会把它们归为 BYOVD 并拦截，属预期行为。
- 所有写入都是**易失寄存器**：不刷 VBIOS、不烧熔丝，断电即恢复。
- 熔丝值读取依赖社区/固件命名映射，已在文中逐条标注等级；"读不到"和"不存在"是两句话。
- 本文**不**声称 x16 能带来带宽提升；那是物理层实验，需要补 AC 耦合电容并实测验证。
