# P104-2.0x16 位穷举（"软件拦宽度"假设）实测报告 — 2026-10-31

> 目标：用户假设"宽度被某个软件位拦住"，要求穷举排查。
> 方法：停保持进程 → 只读基线 → 对 7 个寄存器逐位单变量写 + 根端口 retrain + 读宽度 + 回滚。
> 结论先行：**117 位全扫，没有一位能改变宽度（恒 x4）或芯片侧宽度镜像 `0x8C080`（恒 0x0404）；软件位层面不存在"拦住宽度"的门。** 扫描收尾时卡掉线（非车道数字段位所致），需 **AC 断电 30 秒**。

---

## 0. 授权与安全边界

- 用户已授权：允许写寄存器、允许掉卡（AC 断电 30 秒恢复）。
- 本次实际动作只有两类：BAR0 MMIO 单 dword 写；根端口 PCIe 配置 `LNKCTL.bit5=1`（Retrain Link）。
- **未做**：`LNKCTL.bit4`（Link Disable）、SBR、VBIOS/EEPROM 写、竞品 EFI、git/gh、改 relay / 工具源码 / exe。
- 每步固定动作：单 bit 异或 → 写后回读 → 根端口 retrain → 1.0 s 紧循环采样两端 `LNKSTA` → 读 `0x8C080`×3 → 回滚 → 回读校验 → ≥1 s 间隔。
- `0x8C040` 写前硬断言：只允许单 bit 变化，且结果必须 `bit31=1 且 bit29=0`（两个掉卡象限直接拒绝）。
- 脚本自带掉卡判据：端点 `cfg0 != 0x1B8710DE` 立即 Abort，不重试。

## 2. 扫描方法与预算

- 脚本：`_gh/v11/test/widthproc/bitsweep.py`（新增，未改任何既有文件）。
- 分组：`c040`(27) → `regs`(90) → `lanefield`(3)，计划 **120 步**；实际完成 **117 步**（第 118 步在写之前因掉卡中止）。
- 每次写都回读；回读不符 = 该位不可写（硬件强制 0/1 或自清），记录但继续。
- 采样量：117 步共 **12,245,635 次**两端 `LNKSTA` 采样（每步 1.0 s 紧循环），触发 **118 次** retrain。
- 回滚：117/117 成功（`rollback_ok` 全 true），无一位残留。

## 3. 结果总表

| 寄存器 | 扫了哪些位 | 步数 | 宽度变化 | `0x8C080` 变化 | 步末状态 |
|---|---|---|---|---|---|
| `0x8C040` | 0–26（不含 29/31） | 27 | **0** | **0** | 恒 Gen2 x4 |
| `0x8872C` | 0–15 | 16 | 0 | 0 | 恒 Gen2 x4 |
| `0x88150` | 0–14, 31 | 16 | 0 | 0 | 恒 Gen2 x4 |
| `0x8B980` | 0–7, 16–23 | 16 | 0 | 0 | 恒 Gen2 x4 |
| `0x8C1C0` | 0–7, 16,17,20,21 | 12 | 0 | 0 | 恒 Gen2 x4 |
| `0x8C2C0` | 0–14 | 15 | 0 | 0 | 恒 Gen2 x4 |
| `0x8C300` | 0–14 | 15 | 0 | 0 | 恒 Gen2 x4 |

- **没有任何一步**在任何一次采样里出现过宽度 >4（连 x8 的瞬态都没有）。
- `0x8C080` 在 117×3 = 351 次读取里**全部**是 `0x00000404`。
- 每步末 `(speed,width)` 组合集合只有 `(2,4)` 一个值；根端口同宽。

### 3.1 哪些位根本写不进（本次扫描的副产品）

| 寄存器 | 可写位 | 写不进（只读/自清/强制） |
|---|---|---|
| `0x8C040` | 2,3,7–15,18–26 | **0,1,4,5,6,16,17** |
| `0x8872C` | **只有 0–3** | 4–15 全部硬 0 |
| `0x88150` | 0–4,6,7,8,31 | 5,9–14 |
| `0x8B980` | 0–7,16–23（扫到的全可写） | — |
| `0x8C1C0` | 1,3,4,5,6,16,17 | 0,2,7,20,21 |
| `0x8C2C0` | 0–14 全可写 | — |
| `0x8C300` | 0–14 全可写 | — |

解读（仅限"看到的"）：
- `0x8C040` bit0（LTSSM_DIRECTIVE.CHANGE_SPEED）与 bit1 都是**自清位**，写 1 后回读立即为 0——与"触发类位"一致；
- `0x8C040` bit4（LTSSM_STATUS）、bit5/6、bit16/17 不可写；
- `0x8872C` 只有低 4 位存在（FUSE_OVERRIDE 字段），高位是硬 0 ⇒ 之前"mask 0x80/0x100/0x20000000"类写法在**这个寄存器**上不可能有效（那些 mask 属于 `0x88150`）。

### 3.2 唯一产生了链路行为的位：`0x8C040` bit11

| 位 | 写入 | 25 ms 后两端 `LNKSTA` | 宽度 | 恢复 |
|---|---|---|---|---|
| bit11 | `0x80045800 → 0x80045000`（清 bit11） | `EP=0x1041 / RP=0x7041` → **降到 Gen1(2.5GT/s)** | 仍 **x4** | 回滚 + 补 1 次 retrain 后回 `0x1042`（Gen2 x4） |

- 即：**bit11=1 是"跑 Gen2"的必要条件**（清掉就掉 Gen1），但它与宽度无关；
- 其余 116 位：写进去、链路不动（Gen2 x4 不变）；
- 这也是全部 117 步里唯一一次需要"回滚后补训"的步。

|---|---|---|

### 5.1 `0x4B12` 起的 `{addr, mask, value}` 12 字节表（两条 `0x8C040`）

```
0x04B2A: addr=0x88088 mask=0x000F0000 value=0x00010000
0x04B36: addr=0x8C040 mask=0x000C0000 value=0x00080000   → SPEED[19:18]=2  (2.5GT/s, Gen1)
0x04B42: addr=0x8C040 mask=0x0000001F value=0x00000000   → 清 LTSSM 指令/状态低位
0x04B4E: addr=0x21328 mask=0x00000008 value=0x00000008
```

### 5.2 `0x6E` 形式的 devinit 写（`6E <addr32> <mask32> <value32>`，`new=(old&~mask)|value`）

```
0x0C9AC: 6e 40c00800 f0ffffff 01000000  → (old & ~0xF) | 1  = LTSSM_DIRECTIVE=CHANGE_SPEED
0x0C9BE: 6e 40c00800 f0ffffff 02000000  → (old & ~0xF) | 2  = 置 bit1（CHANGE_WIDTH 位）
0x0C9DC: 6e 40c00800 ff37ffff 00480000  → 清 bit15、置 bit11/bit14（bit11 正是 §3.2 的 Gen2 位）
0x0C91E / 0x0C9CF: 6e 00c10800 ffffffff 00000000 → 0x8C100 = 0
```

（第 6 处 `0xC99C` 前一个字节是 `0x00` 而不是 `0x6E`，是另一条指令里的立即数/对齐残留，不作为写入证据。）

### 5.3 结论（VBIOS 侧）

- VBIOS 对 `0x8C040` 只写 **LTSSM 指令位、SPEED 字段、bit11/14/15**；
- **从不碰 `[31:27]` 车道数字段、从不置 bit31（arm）**；
- **从不写 `0x8C080`**（全镜像 0 次出现）。
- ⇒ 启动时的 x4 **不是 VBIOS 写出来的**，是 strap/PHY 训练结果；也能解释为什么写 `0x8C040[31:27]` 只改变声明（`LNKCAP`）而不改变实际宽度。

## 7. 结论与覆盖边界

**结论**：在"软件位拦宽度"这个假设下，本次穷举给了否定答案——
117 位单变量、1224 万次采样、118 次 retrain，**没有一位**能改变实际链路宽度或 `0x8C080`；
VBIOS 也从不配置车道数。宽度不是被某个可写位"拦住"，而是训练时根本只要到 4 条 lane。

**已覆盖**：`0x8C040` bit0–26；`0x8872C` 0–15；`0x88150` 0–14/31；`0x8B980` 0–7/16–23；`0x8C1C0` 0–7/16/17/20/21；`0x8C2C0` 0–14；`0x8C300` 0–14。

**未覆盖（诚实声明）**：
1. `0x8C040` bit27/28/30（会把 `[31:27]` 改成 17/18/20，属危险区）——**因掉卡中止，未测**；
2. `0x8872C` 16–31、`0x88150` 15–30、`0x8B980` 8–15/24–31、`0x8C1C0` 8–15/18–19/22–31、`0x8C2C0`/`0x8C300` 15–31（受 120 步预算限制）；
3. `0x8C004 = 0x0000FFFF`（16 lane 位图候选）与 `0x8C3C0` 索引表——本次未扫。
   续扫命令（卡恢复后可直接用）：
   ```
   python bitsweep.py --step baseline
   python bitsweep.py --step sweep --group lanefield     # 27/28/30
   ```
   若要扫 `0x8C004`：把 `0x8C004` 加进 `PLAN`（bits 0–15）即可，脚本无需改动。

**风险提示**：掉卡与 lane-field 位无关，但 `0x8C040[31:27]` 改成 17/18/20 后再 retrain 的行为仍未知，续扫前应先确认卡已完全恢复。
